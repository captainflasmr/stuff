1. (Biggest win) Disable Gradle importer — use Eclipse .project files instead
Since .project/.classpath are already present and maintained, there's no need for Buildship/Gradle import. Add to your jdtls JVM args:
-Djava.import.gradle.enabled=false
-Djava.import.maven.enabled=false
This forces JDTLS to use EclipseProjectImporter which just reads the XML files — seconds, not minutes. The 14 .classpath files already define all source paths, dependencies, and output dirs.
Caveat: If you change dependencies in build.gradle.kts, you'll need to regenerate .classpath (via ./gradlew eclipse or similar) or temporarily re-enable Gradle import.
---
2. Ensure .data directory is stable (prevent re-syncs)
Your log shows fedproclient-java-java was modified since last time the workspace was opened, must be synchronized. This triggers a full Gradle re-sync every time any file changes. To prevent this:
- Don't delete the .data directory between sessions
- Use a fixed path (you already do)
- If using lsp-mode in Emacs, ensure it reuses the same -data dir
---
3. Remove -Dorg.gradle.daemon=false
This flag runs Gradle in-process each time, which is slower for multi-project builds. For the Gradle import that does run, the daemon could cache project models. Since you're offline, there's no downside to letting the daemon run.

4. Increase heap if possible
You're at -Xmx4G. With 14 subprojects and 167k lines, 6G might help GC pauses but is unlikely to be a primary bottleneck. Only increase if you have RAM to spare.
