5 minutes is painful but common for large Java projects. Here are the most effective ways to reduce it:

## Give JDT LS more heap

The biggest win is usually just more memory. In your `jdtls` launch args:

```
-vmargs -Xms512m -Xmx4g -XX:+UseG1GC
```

More heap = fewer GC pauses during indexing. `-XX:+UseG1GC` handles large heaps better than the default collector.

## Use a faster JDK

JDT LS runs on JVM — use JDK 17+ to launch the server itself (separate from your project's JDK). Newer JVMs have significantly better startup and GC characteristics.

## Exclude directories from watching

If you have large generated directories, build outputs, or node_modules nearby:

```elisp
(setq eglot-ignored-server-capabilities '())

;; Or configure file watching exclusions via workspace config
```

In `.settings/org.eclipse.core.resources.prefs` or via LSP workspace settings, exclude `target/`, `build/`, `.gradle/` from indexing.

## Persist the workspace cache

Make sure JDT LS is reusing its `-data` workspace directory between sessions rather than a temp dir. If it's a fresh dir each launch, it re-indexes every time. Point it at a stable path:

```
-data ~/.cache/jdtls-workspace/my-project
```

## Limit project scope

If it's a multi-module Maven/Gradle project, JDT LS indexes everything. You can open just the submodule you're working on rather than the root, which dramatically cuts indexing scope.

## Check if Gradle/Maven itself is slow

Sometimes the delay isn't JDT LS indexing — it's JDT LS waiting for Gradle/Maven to resolve dependencies. Running `gradle dependencies` or `mvn dependency:resolve` first to warm the local repo cache helps isolate whether that's the bottleneck.

---

The **stable `-data` directory + more heap** combination alone usually cuts startup from 5 minutes to under 30 seconds on subsequent launches, since the index is already built and just needs to be validated.
