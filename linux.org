I run [[https://opencode.ai][opencode]] as my primary agentic coding tool.  It has one annoying default: every step — title generation, deep refactor planning, and the actual file edits — runs on whatever single model you set.  That means either burning a frontier-rate thinking model on boilerplate text operations, or pinning a cheap fast model and losing reasoning depth on the hard parts.  There is a better split.

The plan: keep the *thinking* on a frontier reasoning model, and dump all the *donkey work* on a cheap, fast model.  GLM-5.2 does the planning, Deepseek V4 Flash implements.  Total cost drops, quality on the hard bits stays high.

#+hugo: more

** The shape of the split

opencode's [[https://opencode.ai/docs/agents][agents]] are configurable: each one pins a =model=, a =reasoningEffort=, a =mode= (primary / subagent / all), and a =permission= ruleset.  Two agents matter most:

- =plan= — the entry point.  Reads, reasons, plans at file level, then delegates.  Read-only: never edits, writes, or shells itself.
- =build= — the worker.  Receives a precise, self-contained task from =plan= and executes it.  Cheap reasoning, fast iteration.

Two helpers fill in around them: =explore= (cheap codebase scans, so the planner doesn't waste tokens reading everything) and =general= (frontier thinking for non-trivial research).  Background housekeeping — =title=, =summary=, =compaction= — all go to the cheap model too.  Nothing expensive runs for boilerplate.

** The config

The whole thing lives in =~/.config/opencode/opencode.json=:

#+begin_src json
{
    "$schema": "https://opencode.ai/config.json",
    "model": "opencode-go/deepseek-v4-flash",
    "small_model": "opencode-go/deepseek-v4-flash",
    "default_agent": "plan",
    "subagent_depth": 1,
    "agent": {
        "plan": {
            "mode": "primary",
            "model": "opencode-go/glm-5.2",
            "steps": 50,
            "reasoningEffort": "max",
            "prompt": "{file:prompts/glm-planner.md}",
            "permission": {
                "read": "allow", "glob": "allow", "grep": "allow",
                "list": "allow", "webfetch": "allow", "task": "allow",
                "question": "allow",
                "edit": "deny", "write": "deny", "bash": "deny",
                "todowrite": "deny"
            }
        },
        "build": {
            "mode": "all",
            "model": "opencode-go/deepseek-v4-flash",
            "steps": 100,
            "reasoningEffort": "low",
            "permission": {
                "read": "allow", "glob": "allow", "grep": "allow",
                "list": "allow", "edit": "allow", "write": "allow",
                "bash": "allow"
            }
        },
        "explore":     { "model": "opencode-go/deepseek-v4-flash", "reasoningEffort": "low" },
        "general":     { "model": "opencode-go/glm-5.2",           "reasoningEffort": "medium" },
        "title":       { "model": "opencode-go/deepseek-v4-flash", "reasoningEffort": "low" },
        "summary":     { "model": "opencode-go/deepseek-v4-flash", "reasoningEffort": "low" },
        "compaction":  { "model": "opencode-go/deepseek-v4-flash", "reasoningEffort": "low" }
    }
}
#+end_src

A few choices worth flagging:

- =default_agent: plan= — default flows through GLM.  Trivial questions resolve in one GLM turn; anything heavier triggers delegation.
- =small_model= pinned to Deepseek — used by opencode for titles, chat summaries, compaction.  Keeps the per-turn cost floor low.
- =build.mode: "all"= — the worker is reachable both via delegation (subagent) *and* as a directly-selectable primary, for a one-shot "just make this tiny edit" without paying for a planning pass.
- =subagent_depth: 1= — =build= cannot launch its own subagents.  Without this cap a cheap worker happily spawned nested research and the cost climbed past the planner's.
- =plan.permission.task: "allow"= is the one that makes it work — without it, =plan= has no way to delegate and would have to do edits itself, which it can't (=edit: deny=).

** The planner prompt

opencode resolves =prompt: "{file:...}"= at startup and injects the file body as the agent's system prompt.  The =plan= agent uses a dedicated prompt that hammers the delegation contract — pass it tasks that are self-contained, because the subagent starts from a fresh context unless you give it one.

#+begin_src markdown
# GLM-5.2 — Lead Planner / Orchestrator

You are the lead architect. You do the *thinking*; a cheap fast worker does the *typing*.

## Role
- Reason carefully about the request and the codebase before acting.
- Produce a concrete, file-level plan: what changes, where, in what order, and why.
- Then DELEGATE implementation to the `build` subagent via the task tool.
- You are read-only: never edit, write, or run shell yourself. You think and direct.

## Work cheap and smart
- Delegate broad codebase scans to the `explore` subagent instead of reading everything yourself.
- Delegate implementation to `build` with a precise, self-contained task: exact files,
  exact changes, constraints. Do not assume `build` shares your context.
- Review `build`'s result by reading the changed files. If wrong, delegate a corrective task;
  never redo the work yourself.
- Batch independent subtasks; sequence dependent ones.
#+end_src

** How a request actually flows

A real change walks this path:

1. You ask for something.  =default_agent= routes to =plan= (GLM-5.2, =max= reasoning).
2. =plan= reads the relevant files directly (cheap) or delegates the search to =explore= (cheaper still).
3. =plan= emits a plan: file list, per-file changes, order, risks.
4. =plan= calls the =task= tool with one self-contained task.  =build= (Deepseek, =low= reasoning) executes it in its own context — =steps: 100= gives it room to iterate.
5. =plan= reads the result.  On a miss, =plan= delegates a corrective task rather than fixing it itself.

The cost shape is what you would expect: GLM tokens go on reasoning + review reads, Deepseek tokens on the churn of writing and re-running tools.  Most of the agent loop is Deepseek; the expensive model only touches the hard decisions.

** Two gotchas

1. *Reasoning effort is provider-specific.* =reasoningEffort= is an options-passthrough, not a schema enum — opencode forwards it to the provider.  =low= is the safest universal value.  If your provider ignores it, the worker silently burns reasoning tokens anyway; check the provider docs before trusting it.
2. *Subagent context is fresh.* The =task= tool spawns =build= with only what you pass it.  Call-by-call the planner must re-send the specifics — file paths, exact diffs, constraints — or the worker guesses and gets it wrong.

** Force-planning mode (optional)

If you would rather GLM plan *every* edit and never let you skip straight to =build=, flip =build.mode= from ="all"= to ="subagent"=.  It then becomes unreachable as a primary agent and only fires when =plan= delegates to it.  I keep it on ="all"= for the quick-edit escape hatch.

** Applying it

opencode loads its config once at startup and does not hot-reload.  After saving =opencode.json= and any prompt files, quit opencode and relaunch.  To debug a broken config without losing the session, set:

#+begin_src bash
OPENCODE_DISABLE_PROJECT_CONFIG=1 opencode
#+end_src

That skips the broken project config and boots from globals, so you can edit the file and restart cleanly.

Getting screen brightness control working on a Samsung Galaxy Book Pro 360 running Arch Linux and Sway.  Out of the box, the brightness keys do nothing and the =intel_backlight= sysfs interface reads zero despite the screen being on.  Two kernel parameters and a udev rule fix it completely.

#+hugo: more

** Why it breaks

The Samsung Galaxy Book Pro 360 uses a 12th-gen Intel Alder Lake CPU with Iris Xe Graphics.  Its display is controlled over eDP using DPCD (DisplayPort Configuration Data) commands rather than traditional PWM backlight.  On a stock Arch install two things go wrong:

1. The ACPI video subsystem claims the backlight device ahead of the native Intel driver, so =/sys/class/backlight/intel_backlight/brightness= reads =0= and writes are silently ignored by the hardware.
2. Even once ACPI stops interfering, the i915 driver defaults to PWM backlight control, which does nothing on a DPCD panel.

** The fix

*** 1. Add kernel parameters to GRUB

Edit =/etc/default/grub= and append two parameters to =GRUB_CMDLINE_LINUX_DEFAULT=:

#+begin_src bash
sudo sed -i 's/GRUB_CMDLINE_LINUX_DEFAULT="\(.*\)"/GRUB_CMDLINE_LINUX_DEFAULT="\1 acpi_backlight=native i915.enable_dpcd_backlight=3"/' /etc/default/grub
sudo grub-mkconfig -o /boot/grub/grub.cfg
#+end_src

- =acpi_backlight=native= stops the ACPI video driver from claiming the backlight, leaving it for the native i915 driver.  Without this, =intel_backlight= stays stuck at 0.
- =i915.enable_dpcd_backlight=3= forces the i915 driver to use DPCD commands for brightness.  The =3= means force-enable and ignore the Video BIOS Table (VBT), which is necessary because Samsung's VBT does not advertise DPCD support correctly on Linux.

*** 2. Create a udev rule for non-root access

By default only root can write to the backlight sysfs node.  This rule grants the =video= group write access whenever the device is added:

#+begin_src bash
echo 'ACTION=="add", SUBSYSTEM=="backlight", RUN+="/bin/chgrp video /sys/class/backlight/%k/brightness", RUN+="/bin/chmod g+w /sys/class/backlight/%k/brightness"' \
    | sudo tee /etc/udev/rules.d/90-backlight.rules
#+end_src

Your user should already be in the =video= group (verify with =groups=).  If not: =sudo usermod -aG video $USER=.

*** 3. Reboot and verify

After rebooting, check the parameters are active:

#+begin_src bash
cat /proc/cmdline
#+end_src

Then test brightness control directly:

#+begin_src bash
brightnessctl set 50%
#+end_src

The screen should dim or brighten visibly.  The brightness reading in =/sys/class/backlight/intel_backlight/brightness= should now reflect the actual hardware level (e.g. ~15000/65535) rather than 0.

** Sway keybindings

Sway's default config already includes brightness bindings pointing at =brightnessctl=, so the Fn keys should work immediately after the reboot.  If your config does not have them, add:

#+begin_src conf
bindsym --locked XF86MonBrightnessDown exec brightnessctl set 5%-
bindsym --locked XF86MonBrightnessUp exec brightnessctl set 5%+
#+end_src

** bootstrap install.sh

The =step_quirk_samsung_backlight= step in =install.sh= applies both kernel parameters and the udev rule automatically as part of a fresh machine setup.  Run it standalone to re-apply on an existing install:

#+begin_src bash
./install.sh --step step_quirk_samsung_backlight
#+end_src

* TODO Stopping Surfshark VPN from Freezing Thunar, Deluge and My NAS :2026:vpn:nfs:networking:
:PROPERTIES:
:EXPORT_FILE_NAME: 20260602061340-linux--Stopping-Surfshark-VPN-from-Freezing-Thunar-Deluge-and-My-NAS
:EXPORT_HUGO_SECTION: linux
:EXPORT_HUGO_LASTMOD: <2026-06-02 06:13>
:END:

For ages I had a low-level annoyance that I never quite got around to investigating: the moment I connected Surfshark to a VPN server, applications like Thunar and Deluge would take an age to open, and browsing to my =~/nas= directory would hang for what felt like an eternity.  Disconnect the VPN and everything was instant again.

#+hugo: more

It turns out this is not a VPN bug, an app bug, or anything mysterious -- it is a perfectly logical collision between how my NAS is mounted and what a VPN does to your routing table.

** What was actually going on

My NAS is an NFS v3 mount, set up something like this:

#+begin_src text
192.168.0.10:/volume1/Drive on /home/jdyer/nas type nfs (rw,...,hard,timeo=600,...)
#+end_src

Two details matter here.  First, the NAS lives at =192.168.0.10= -- a *different subnet* from my laptop, which sits on =192.168.7.x=.  That means the NAS is only reachable via my default route, through the local router.

Second, and this is the killer, the mount is =hard=.  A hard NFS mount will block indefinitely (well, =timeo=600= means 60 seconds per retry) when the server stops responding, rather than returning an error.

Now connect a VPN.  Surfshark, like any sensible full-tunnel VPN, replaces your default route with the tunnel so that *all* your traffic goes through it.  But "all your traffic" now includes packets bound for =192.168.0.10=.  Those get fired off into the VPN tunnel, where the NAS most certainly does not live, and they vanish into the ether.

The NAS is now unreachable.  And because the mount is =hard=, every single =stat()= on =~/nas= blocks for up to a minute instead of failing fast.  Thunar scans your home directory and bookmarks on startup.  Deluge checks its default download location.  Opening =~/nas= obviously touches it directly.  All of them sit there, frozen, waiting on a mount that is being routed into a black hole.

Mystery solved.

** The fix: split-tunnel the NAS subnet

The clean solution is to tell the system that traffic for the NAS subnet should *always* go via the local router, never via the VPN.  This is a form of split tunnelling, done at the routing level.

The good news is that the Surfshark Linux client uses WireGuard-style policy routing under the hood, with a =suppress_prefixlength 0= rule.  In plain English: it captures the *default* route into the tunnel, but it still honours any *specific* route you have in the main routing table.  So if I add an explicit route for the =192.168.0.0/24= subnet, it wins over the tunnel.

Since I use NetworkManager, the tidiest way is to bake the route straight into my Wi-Fi connection profile so it is always present and survives reboots:

#+begin_src bash
nmcli connection modify STRONG_ATRIA_F6NF +ipv4.routes "192.168.0.0/24 192.168.7.254"
nmcli connection up STRONG_ATRIA_F6NF
#+end_src

Substitute your own connection name (=nmcli connection show --active=), your NAS subnet, and your router's address.

To verify, with the VPN connected:

#+begin_src bash
ip route get 192.168.0.10
#+end_src

The output should show the path going =via 192.168.7.254 dev wlo1= -- my local router and Wi-Fi interface -- and crucially *not* a =wg= or =tun= device.  If it does, NAS traffic is bypassing the tunnel, and Thunar, Deluge and =~/nas= all spring open instantly again, VPN or no VPN.

To undo it, swap the =+ipv4.routes= for =-ipv4.routes= with the same value.

** A note on security

Some people get twitchy about routing anything outside the VPN.  In this case the bypassed traffic is purely LAN-local -- it never leaves my house and never touches the internet -- so there is nothing here that the VPN was protecting in the first place.  This is exactly the kind of traffic you *want* to exclude from a tunnel.

I wrapped the whole thing up in a little =nas-bypass= script in =~/bin= so future-me can re-apply or check it without having to remember the incantation.

I am always fiddling around with wallpapers, themes, backgrounds and the like, so it was only a matter of time before I wanted my Sway window decorations to actually match my wallpaper rather than the same static Nord palette I have been staring at for years.

#+hugo: more

Don't get me wrong, Nord is great, and it has served me well, but once you start using pywal to generate colour palettes from your wallpaper, having your terminal, GTK apps, and waybar all shift to match while those window titlebars sit there in stubborn #434c5e starts to feel, well, a bit disjointed.

So I did what any self-respecting tiling WM user would do: I made them obey pywal too.

I already had pywal running on wallpaper change via a simple script, and my Sway config had the usual hardcoded =client.focused= and friends in =config.d/theme=:

#+attr_org: :width 300px
#+attr_html: :width 100%
[[file:static/linux/20260516091728-emacs--Pywal-and-Sway-Dynamic-Window-Decorations-from-Your-Wallpaper.jpg]]

That is five colour fields per line, by the way -- border, background, text, indicator, and child_border -- and I was setting them all to pre-selected Nord values that never changed no matter how leafy or dark my wallpaper was.

I ended up with a two-layer solution because colours need to work at two different times:

1. On Sway start or reload -- the config file needs the right colours baked in from the start.
2. On wallpaper change -- colours need to update live without restarting Sway.

Pywal supports custom templates.  You drop a file in =~/.config/wal/templates/= with placeholder variables like ={foreground}=, ={background}=, ={color1}= etc, and pywal expands them when it runs.  The output lands in =~/.cache/wal/= with the same filename.

So I created =~/.config/wal/templates/sway=:

#+begin_src conf
# Pywal-generated colors for Sway
client.focused          {foreground}  {background}  {foreground}  {color5}  {color6}
client.focused_inactive {color8}      {background}  {color8}      {color4}  {color4}
client.unfocused        {color8}      {background}  {color8}      {color4}  {color4}
client.urgent           {color1}      {color1}      {background}  {foreground}  {color1}
#+end_src

The mapping is fairly intuitive: focused windows get the foreground colour for borders and text with a subtle accent on the indicator, while unfocused ones drop back to a muted =color8= so they sit quietly in the background.  Urgent windows invert and use =color1= (the red-ish accent) as the dominant colour.

Then I added one line to =config.d/theme=:

#+begin_src conf
include ~/.cache/wal/sway
#+end_src

Now every time I reload Sway (=Mod4+o=, in my setup), it picks up whatever pywal's current palette is.  No more Nord-by-default.

Sway reload is fine for a one-off, but I change wallpapers pretty regularly (bound to =Mod4++=) and I want the colours to shift immediately.  Enter =swaymsg=.

My =wallpaper_change.sh= script already ran pywal and set the wallpaper, so I just needed it to also poke the window decoration colours at runtime.  The critical bit:

#+begin_src bash
# Load colors from pywal
colors=$(cat ~/.cache/wal/colors.json)

fg=$(echo $colors | jq -r '.special.foreground')
bg=$(echo $colors | jq -r '.special.background')
c1=$(echo $colors | jq -r '.colors.color1')
c4=$(echo $colors | jq -r '.colors.color4')
c5=$(echo $colors | jq -r '.colors.color5')
c6=$(echo $colors | jq -r '.colors.color6')
c8=$(echo $colors | jq -r '.colors.color8')

# Update sway window decorations
swaymsg client.focused          "$fg" "$bg" "$fg" "$c5" "$c6"
swaymsg client.focused_inactive "$c8" "$bg" "$c8" "$c4" "$c4"
swaymsg client.unfocused         "$c8" "$bg" "$c8" "$c4" "$c4"
swaymsg client.urgent            "$c1" "$c1" "$bg" "$fg" "$c1"
#+end_src

The order of those five arguments to =swaymsg client.focused= is: border, background, text colour, indicator colour, child_border colour.  It matches the Sway config format exactly, so I kept the same mapping I used in the template.

Now when I flip to a warm, earthy wallpaper, my window borders warm up too.  Dark wallpapers give dark, moody borders.  It is a small thing, but it makes the whole desktop feel coherent in a way that partial theming never quite achieves.

And because the template and the =swaymsg= calls share the same colour mapping, everything stays in sync regardless of whether the colours were loaded at Sway startup or pushed live mid-session.

If you are already running pywal with Sway, this is about ten lines of config and a tiny template.  Well worth the five minutes.

The full dotfiles are at [[https://github.com/captainflasmr/dotfiles][github.com/captainflasmr/dotfiles]], and as always, I will probably tweak the colour assignments as different wallpapers expose edge cases!

I wanted one keystroke (and sunrise/sunset automation) to flip my whole Sway session between light and dark: GTK apps, Thunderbird, Emacs, and the terminal. My first attempt was a shell script that rewrote =~/.config/gtk-3.0/settings.ini= and called it a day — but GTK apps only read that file at startup, so nothing actually changed live until I restarted everything. The right tool for the job turned out to be [[https://darkman.whynothugo.nl/][darkman]].

** What darkman gives you

A tiny background service that:

- Tracks sunrise/sunset for your location and flips mode automatically.
- Exposes the current mode over D-Bus and the xdg-desktop-portal =color-scheme= property, which modern GTK4/libadwaita apps, Firefox, Thunderbird, Chromium and Electron all respect live.
- Runs user scripts on every transition so you can hook in anything that doesn't listen to the portal (Emacs, terminal, etc.).
- Has a =darkman toggle= command you can bind to a key.

** Install and configure

On Arch:

#+begin_src bash
sudo pacman -S darkman
#+end_src

Create =~/.config/darkman/config.yaml=. I started with =usegeoclue: true= but geoclue refused the connection on a bare Sway setup (no desktop agent to authorise non-system apps), leaving darkman in a one-crash-per-minute restart loop. A static lat/lng is simpler and rock-solid — location changes aren't frequent enough to matter:

#+begin_src yaml
lat: 50.80
lng: -1.09
portal: true
#+end_src

Enable the user service:

#+begin_src bash
systemctl --user enable --now darkman.service
darkman get        # should print "dark" or "light"
#+end_src

** Transition hooks — mind the directory

This is the bit that tripped me up. Darkman looks for hook scripts under =$XDG_DATA_HOME= (=~/.local/share/=), *not* =$XDG_CONFIG_HOME=. I spent a while wondering why my scripts in =~/.config/dark-mode.d/= were being ignored until I checked the man page:

#+begin_quote
Scripts are searched in a directory named =darkman= inside paths defined in the XDG_DATA_DIRS as well as XDG_DATA_HOME.
#+end_quote

The modern format is a single script under =~/.local/share/darkman/= that receives =dark= or =light= as =$1=.

*** GTK and libadwaita

The key insight: =gsettings set org.gnome.desktop.interface color-scheme= triggers live updates in every running GTK3/4/libadwaita app. No restart required. I still rewrite =settings.ini= so freshly-launched apps start in the right mode.

=~/.local/share/darkman/gtk.sh=:

#+begin_src bash
#!/bin/sh
GTK_CONFIG="$HOME/.config/gtk-3.0/settings.ini"

case "$1" in
    dark)
        SCHEME='prefer-dark'
        THEME='Adwaita-dark'
        PREFER=1
        ;;
    light)
        SCHEME='prefer-light'
        THEME='Adwaita-light'
        PREFER=0
        ;;
    *) exit 0 ;;
esac

gsettings set org.gnome.desktop.interface color-scheme "$SCHEME"
gsettings set org.gnome.desktop.interface gtk-theme "$THEME"
gsettings set org.gnome.desktop.interface icon-theme 'Adwaita'

if [ -f "$GTK_CONFIG" ]; then
    sed -i "s/^gtk-theme-name=.*/gtk-theme-name=$THEME/" "$GTK_CONFIG"

** Takeaways

- Editing =settings.ini= looks like it should work but it's a dead end; apps only read it at startup. =gsettings= is the live-switching path for GTK.

### Steps to resolve:

1. **Fetch the latest changes**
   ```bash
   git fetch origin
   ```

2. **Rebase your local changes on top of the remote `main`**  
   This applies your local commits after the latest remote changes.
   ```bash
   git rebase origin/main
   ```

   - If there are no conflicting changes, this should complete successfully.
   - If there are conflicts, Git will pause and ask you to resolve them.

3. **Resolve any merge conflicts (if prompted)**
   - Open the conflicting files, manually resolve conflicts.
   - Mark them as resolved:
     ```bash
     git add <file>
     ```
   - Continue the rebase:
     ```bash
     git rebase --continue
     ```

4. **Push your changes**  
   Now that your branch is up to date with the remote, you can push:
   ```bash
   git push origin main
   ```

### Alternative: Merge Instead of Rebase
If you prefer to merge the remote changes instead of rebasing:

```bash
git push origin main
```

*** USB Standards and Speeds

- **USB 2.0:** Offers transfer rates up to 480 Mbps, but real-world speeds often hover around 30-40 MB/s for reads.
- **USB 3.0 (also known as USB 3.1 Gen 1):** Officially supports speeds up to 5 Gbps. Typical real-world read speeds might range from 100 MB/s to 400 MB/s, depending on the device.
- **USB 3.1 (also known as USB 3.1 Gen 2):** Doubles the potential throughput to 10 Gbps. Real-world speeds for high-quality drives can range from 300 MB/s to close to 1 GB/s for some external SSDs.
- **USB 3.2:** Not as widespread in terms of devices at the time of writing, but it potentially offers up to 20 Gbps for devices supporting the standard.
- **USB 4:** Offers speeds up to 40 Gbps under ideal conditions, but devices utilizing this standard are still not as common. Speeds will highly depend on the devices and setups involved.

*** Drive Types

- **HDD:** External HDDs are limited by their mechanical nature, with speeds often falling in the range of 80-160 MB/s for USB 3.0 and above interfaces.
- **SSD:** External SSDs can take better advantage of faster USB interfaces, with read speeds potentially reaching up to and exceeding 1 GB/s for USB 3.1 and later, assuming the drive's internal speed supports it.
- **Flash Drives:** Speeds can vary widely based on the quality and design of the flash drive, from as slow as 10 MB/s for low-end USB 2.0 drives to 400 MB/s or more for high-end USB 3.1 (and beyond) flash drives.

*** Other Factors

- **File System:** The type of file system (e.g., NTFS, FAT32, exFAT, HFS+, ext4) can affect speeds due to differences in efficiency and overhead.
- **File Size and Type:** Smaller files can take longer to transfer overall than large files due to overhead. A large number of small files can significantly reduce the speed.
- **Computer and Port:** The USB port's specification on your computer and how it handles data can also impact speeds. Older computers may not fully leverage the speeds offered by newer USB standards.

*** Typical Ranges

- USB 2.0 drives: **20-40 MB/s**
- USB 3.0/3.1 drives: **100-400 MB/s**
- High-end USB 3.1/3.2 SSDs: **up to 1 GB/s or slightly more**

6. Adjust the values to your desired sensitivity level by typing "xinput set-prop [touchpad ID] [property ID] [scroll amount]" and press enter. Replace [property ID] with the ID number of “Scrolling Distance,” and [scroll amount] with the number you want.

My external USB backup drive started misbehaving: it took ages to mount, sometimes did not mount at all, and when it did mount it would flip itself to *read-only* within seconds.  It turned out to be two problems feeding each other -- a buggy USB-to-SATA bridge and a corrupted ext4 filesystem -- and crucially they had to be fixed *in the right order*, or the repair simply would not stick.

#+hugo: more

The drive (=/dev/sda1=, ext4, label =Backup=, mounted at =/run/media/jdyer/Backup=) appeared to mount fine, then a write test would fail:

#+begin_src bash
touch /run/media/jdyer/Backup/.writetest
# touch: cannot touch ...: Read-only file system
#+end_src

The mount table still claimed =rw=, but the kernel had silently remounted it read-only to protect the data.  The kernel log told the real story.

A look through the kernel ring buffer revealed both problems at once:

#+begin_src bash
sudo dmesg | grep -iE 'sda|uas|usb-storage|EXT4'
#+end_src

*Problem 1 -- the filesystem was corrupt.*  Seconds after mounting, ext4 aborted its journal and went read-only:

#+begin_src text
EXT4-fs error (device sda1): ext4_validate_block_bitmap: bg 125: bad block bitmap checksum
Aborting journal on device sda1-8.
EXT4-fs (sda1): Remounting filesystem read-only
#+end_src

The =errors=remount-ro= mount option is doing its job here -- detecting metadata corruption and flipping read-only rather than risk writing more garbage.

*Problem 2 -- the USB bridge kept dropping out.*  The enclosure uses a *JMicron 152d:a578* bridge running in UAS (USB Attached SCSI) mode, and its firmware is buggy:

#+begin_src text
uas_eh_device_reset_handler FAILED err -19
Synchronize Cache failed: hostbyte=DID_NO_CONNECT
usb 4-2: USB disconnect
#+end_src

JMicron bridges are notorious for flaky UAS firmware.  That disconnect-mid-write is almost certainly what corrupted the filesystem in the first place -- which means repairing the filesystem *without* fixing the bridge would just let it happen again.

Before trusting the drive with backups, I confirmed the physical disk was healthy with SMART:

#+begin_src bash
sudo pacman -S smartmontools
sudo smartctl -a /dev/sda
#+end_src

The numbers that matter were all pristine:

#+begin_src text
SMART overall-health self-assessment test result: PASSED
  5 Reallocated_Sector_Ct    0
197 Current_Pending_Sector   0
198 Offline_Uncorrectable    0
199 UDMA_CRC_Error_Count     0
#+end_src

So the platter was fine.  The corruption was the *bridge*, not failing media -- exactly the right conclusion to commit to before doing anything destructive.

This is the bit that caught me out.  My first instinct was to unmount and run =e2fsck= straight away:

#+begin_src bash
umount /run/media/jdyer/Backup
sudo e2fsck -f -y /dev/sda1
#+end_src

It fixed "some things" and a second pass reported clean.  But after a replug the *exact same* =bg 125= error came straight back.  Running =e2fsck= over the still-unstable UAS link is worse than useless: its repair writes were being dropped or never flushed, so the "clean" result was a lie -- the platter still held the corruption.

*Fix the bridge first.*  The cure for the JMicron UAS bug is a usb-storage quirk that forces the slower-but-stable BOT (Bulk-Only Transport) mode instead of UAS:

#+begin_src bash
echo 'options usb-storage quirks=152d:a578:u' | sudo tee /etc/modprobe.d/usb-quirks.conf
#+end_src

After a reboot, confirm the quirk took effect:

#+begin_src bash
dmesg | grep -i uas
# usb 4-2: UAS is ignored for this device, using usb-storage instead
# usb-storage 4-2:1.0: Quirks match for vid 152d pid a578: 800000
#+end_src

No more =uas_eh_device_reset= or =DID_NO_CONNECT= lines -- the connection was finally stable.

*Then repair the filesystem.*  With a reliable link, =e2fsck= could finally do real work:

#+begin_src bash
umount /run/media/jdyer/Backup
sudo e2fsck -f -y /dev/sda1
#+end_src

This time it found a *huge* amount of damage the earlier bogus run had never touched -- salvaging corrupted directories, fixing hundreds of inode reference counts, and reconnecting around 5,800 orphaned inodes to =/lost+found=.  The file count jumped from 1,677 to 7,544.  Use =-f= to force a full check: a journal abort can leave the superblock looking "clean" so a normal fsck would skip it.

A repair pass that large *must* be followed by a confirming pass.  Run =e2fsck= a third time and check it ends with no =Fix?= prompts and no =FILE SYSTEM WAS MODIFIED=:

#+begin_src text
Pass 1: Checking inodes, blocks, and sizes
...
Pass 5: Checking group summary information
Backup: 7544/61054976 files (1.1% non-contiguous), 62904596/244190208 blocks
#+end_src

Identical counts and no modifications -- proof the repair persisted, which over the old UAS link it never did.

A few practical notes once everything was clean:

- =/lost+found= now holds thousands of recovered files with numeric names.  Because this is a *backup* drive the originals still live on the source, so the cleanest fix is just to re-run the backup and let it restore the proper structure, then clear =lost+found= afterwards.
- That first =rsync= after an fsck re-copies everything, because the repair changes metadata timestamps.  It settles back to fast incremental runs afterwards -- not a cause for alarm.
- Keep the =/etc/modprobe.d/usb-quirks.conf= file in place permanently.  It is the thing that actually fixed the root cause; without it the corruption would simply return.

** The lesson

When a USB disk goes intermittently read-only, resist the urge to reach straight for =fsck=.  Check =dmesg= for UAS resets and disconnects first, rule out the disk with SMART, and *stabilise the connection before you repair the filesystem* -- otherwise you are just writing repairs into a void.

For example a typical title format is the following:

#+begin_example
  Linux ---> Hugo_Format_Title[tag@subtag-art]
#+end_example

and the hugo rendered html of course displays this on a card list and on a single page.  I would like to remove the =Linux --->= part and the tag part to optimise the space taken up by the title.

I am simply just using:

#+begin_example
{{ .Title) }}
#+end_example

which gives the full title.

I want to utilise hugo functions to trim off the front up to the first =->= and to remove the tag part including the closing brackets.

*replaceRE* seems perfect for this to search and replace using regular expressions, so lets give this a go:

#+begin_example
{{ replaceRE "^.*->|\\[.*\\]" "" .Title }}
#+end_example

this gives me:

#+begin_example
Hugo_Format_Title
#+end_example

the only issue I had was to figure out how to escape the bracket character, usually in a regex it is just one backslash, but unfortunately that gave a parse error.  But this can be solved by a double backslash.

Note the use of the pipe character to remove both the prepend with the tags and the removal takes place by defining a replacement string of empty double quotes.

But there is a final thing left to do which I had completely forgotten about, to really tidy up the title I would like to replace the underscores with spaces.  I can't add in another piped OR command as the replacement string has to be a single space and not deleting the text.

The solution is to create a compound nested statement, as thus:

#+begin_example
{{ replaceRE "_" " " (replaceRE "^.*->|\\[.*\\]" "" .Title) }}
#+end_example

so the output string of the original substitution can be fed into another occurrence of *replaceRE*

So the final title is

Hugo Format Title
#+end_example

This is much neater!
